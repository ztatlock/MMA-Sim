# 2026-04-23 — Phase 3.0, hand-specialized ampere-f16

**Status:** landed (workhorse only, ceiling probe)
**Goal:** establish a CPU ceiling for the ampere-f16 workhorse by
compiling out every runtime branch and constant. No kernel
generality; just one tile type done as tightly as reasonable.
Decides whether Phase 3.1 (const-generics rollout) is worth pursuing.

## What changed

- [fastmma_rust/src/lib.rs](../fastmma_rust/src/lib.rs): `mod ampere_f16` with a hand-written
  NEON kernel for (M=16, N=8, K=16, split_k=true, nfb=24, f16→f32).
  All constants baked in. Unrolled k=8 inner loop. Exact-sized stack
  buffers (`[i64; 128]` instead of `[i64; 256]`). f16-specific
  `decompose` skips the f32-subnormal path entirely (f16 values cast
  to f32 never produce f32 subnormals). `mma_ampere_f16_f32_batched_specialized`
  PyO3 entry wraps it in the same rayon pattern as Phase 2.4/2.5.
- [fastmma/rust_ref.py](../fastmma/rust_ref.py): `mma.call_batched_specialized(A, B, C)`;
  raises NotImplementedError for any other (arch, qualifier).
- [bench/batched.py](../bench/batched.py): `spec` column + `spec/s+r` ratio. Gracefully
  shows `—` for non-workhorse rows.

## Where the 1.83× came from

Five places the compiler gets free work when constants are inlined and
the tile shape is fixed:

1. **k-loop unrolling.** `K_HALF=8` fully unrolls; no branch at the
   loop bottom, no induction variable update overhead, register
   allocator can plan the whole 8-iteration sequence.
2. **Branch elision in decompose.** For f16 inputs, the f32-subnormal
   code path is unreachable (f16 subnormals widen to f32 normals).
   Specialized `decompose_f16` drops ~8 instructions worth of branch
   and shift logic per call.
3. **Smaller stack frames.** Generic kernel uses `[i64; 256]` for
   buffers sized at `MAX_ELEMS`; specialized uses `[i64; 128]` for
   `M*K_HALF`. Keeps the whole working set resident in L1.
4. **Constant min_exp, nfb, out_mantissa_bits.** Become immediates
   in the ALU ops instead of register values.
5. **No `if split_k`, `if any_special`, `if n % 2 == 0` at runtime.**
   Dead code eliminated.

I expected maybe 1.3×. 1.83× is the upper end of my guess band.
Reason: the k-unrolling interacts favorably with the NEON code — the
compiler can interleave product collection and the vectorized
accumulate across the 8 unrolled iterations, hiding more latency than
the loop-structured version did.

## Implications for the CPU ceiling claim

Phase 2.5 retrospective projected:
> Per-tile ceiling on CPU is realistically ~2–5 × 10⁴. Further CPU
> work won't cross 10⁵ without GPU.

This phase pushes us to **~1.6 × 10⁴** with just one kernel
specialized. If rolling this out across the remaining instruction
types via const-generics gives similar 1.5–2× lifts, and a further
4-wide NEON (possible for N=8 tiles) adds another 1.5×, we are
plausibly looking at **3–5 × 10⁴×** per-tile before hitting the
hardware wall. The retrospective ceiling was approximately correct;
specialization is pushing us through its lower end sooner than I
guessed.

To cross 10⁵× clearly still needs GPU.

## Code shape notes

- `ampere_f16::tile` copies A's K dimension into two contiguous halves
  on the stack before calling `step` twice. Unavoidable since A[:, :8]
  and A[:, 8:] aren't contiguous in the parent (16, 16) tile layout.
  The copy is 256 f32s = 1 KB per tile, cache-local.
- `decompose_f16` returns `(0, 0)` for NaN/Inf inputs — intentionally
  garbage. The f64 pre-sum (`fp0`, `fp1`) accumulates in parallel and
  the `if !fp.is_finite()` branch short-circuits to the f64 value
  before any int sum is consulted.
- Fallback on non-aarch64 calls `run_one_tile_simd` with the constants
  hand-applied. Same semantics, no measurable lift on those platforms
  (the SIMD fallback in `run_one_tile_simd` is itself scalar there).

## What's next

Phase 3.1 — **const-generics rollout across the instruction set**.
Generalize the pattern into something like:
```rust
fn step<const M: usize, const N: usize, const K_HALF: usize,
        const NFB: i32, const A_MIN: i32, const B_MIN: i32,
        const C_MIN: i32, const OUT_MANT: i32>(...) { ... }
```
and emit monomorphizations for every supported (arch, qualifier).
Compile time goes up; runtime matches the hand-specialized kernel.

Then **Phase 4 — GPU port**, with the specialized kernels as the
clear-eyed template. The specialized structure (fixed shape, no
runtime dispatch, integer-only math) maps directly onto a per-warp
CUDA/Metal kernel.

If 3.1 rolls out cleanly across all 5 current fixtures, we're looking
at ~0.6 μs / tile across the board. At that point another round of
targeted perf work (4-wide NEON via paired vectors, software
pipelining) is the only CPU move left before GPU.

## One open question flagged

Specialization for workhorse now does `ampere_f16::tile`, which
always calls `step` twice (both halves of split-K). That's right for
Ampere. For Turing (m16n8k8, no split-K) and Volta (m8n8k4, no
split-K) the shape is different. The const-generic rollout needs
`K_HALF = K` (single step) vs `K_HALF = K/2` (two steps) as a
compile-time branch. Handleable; just noting it for Phase 3.1's
design.
