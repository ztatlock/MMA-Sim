# 2026-04-23 — Phase 2, Rust kernel (f64 arithmetic)

**Status:** landed (narrow coverage, f64-ported kernel — not yet integer fixed-point)
**Goal:** stand up the Rust/PyO3/maturin pipeline end-to-end. Port the NumPy
reference to Rust using f64 arithmetic (same semantics, no Python/NumPy
overhead). Measure what falls out. Integer fixed-point is deferred to
Phase 2.1 once we know the ceiling here.

## What shipped

- [fastmma_rust/](../fastmma_rust/) — new cargo crate, one function exposed via PyO3:
  `mma_f32_out(A, B, C, nfb, a_min_exp, b_min_exp, c_min_exp, out_mant_bits, split_k)`
- [fastmma/rust_ref.py](../fastmma/rust_ref.py) — Python wrapper that unpacks the oracle's
  parsed ISA fields into the kernel arguments.
- maturin toolchain hooked up; `maturin develop --release` gives an
  editable install of the extension module.

## Results

5 of 10 fixtures validated (the ones the kernel supports), all bit-exact.
Median of 5 reps per instruction, wrapped in the validator's wall-time
timing. "Speedup" is vs. the Python oracle on the same machine.

| label         | rust ms | oracle ms | speedup | numpy_ref ms | vs numpy |
|---------------|---------|-----------|---------|--------------|----------|
| volta-f16     | 0.012   | ~1.9      | 151×    | 0.047        | ~4×      |
| turing-f16    | 0.021   | ~4.8      | 214×    | 0.051        | ~2.4×    |
| ampere-f16 ⭐  | 0.036   | ~9.4      | 237×    | 0.110        | ~3×      |
| ampere-bf16   | 0.067   | ~9.2      | 155×    | 0.106        | ~1.6×    |
| ampere-tf32   | 0.032   | ~7.4      | 213×    | 0.106        | ~3.3×    |

Workhorse (ampere-f16): **9.4 ms → 36 µs, 237×.**

## Interpretation

The Rust/NumPy ratio is *smaller than I expected* (2–4× rather than 10–50×).
Two likely reasons:

1. **Per-call overhead dominates for tiny matrices.** PyO3 dispatch, GIL
   acquire, numpy array unpack, and the `Vec<f32>` materialization inside
   the kernel (I'm copying `a_v.iter().copied().collect()` to get a flat
   slice) are all roughly constant-cost. At 16×8×16 = 2048 products, the
   actual math is ~1–10 µs; overhead is the rest.
2. **The kernel is still doing f64 transcendentals.** `libm::frexp`,
   `f64::powi(2.0, n)` for scaling, `libm::trunc` — these are several
   cycles each. Same ops as NumPy, just without the Python/NumPy layer.

The shape of the result tells us: to get meaningfully past ~200×, the fix
is **not** more Rust — it's the **integer fixed-point rewrite** (Phase 2.1)
that drops all the transcendentals and makes the inner loop pure integer
add/shift/multiply. That's where we expect the jump to 10³–10⁴× per call.

## Scope and bugs

First cut had two semantic bugs, caught by the corpus:

- Hardcoded `nfb = 24` → wrong for Volta (23). Fix: pass `nfb` from Python.
- Hardcoded input `min_exp = F16_MIN_EXP` → wrong for tf32 inputs (which
  decompose at f32's −126, since tf32 has f32's exponent range). Fix: pass
  `a_min_exp`, `b_min_exp`, `c_min_exp` from Python (it already knows via
  the oracle's parsed dtype).

Both caught on the first validator run — corpus working as intended.

Not yet supported by `rust_ref`:
- f64 path (oracle uses serial `libm::fma`; need to match single-rounded
  semantics, natural once we commit to a Rust FMA intrinsic)
- fp8 path (would require exposing the n_fractional_bits=13 / f32_e8m13
  combo — the kernel already supports `out_mantissa_bits=13`, just need
  to widen `_SUPPORTED`)
- fp4, block-scaled, wgmma, tcgen05mma (all a nonzero amount of work each)

## What's next

Phase 2.1 — integer fixed-point rewrite of the same kernel. Strategy:

1. Decompose f16/bf16/tf32/f32 inputs directly from their bit patterns (no
   `frexp` — just mask+shift). Represent each significand as a signed int
   at its natural scale.
2. Multiply significands as ints, add exponents as ints. No f64 involved
   in the inner loop.
3. Align to max_e via signed integer division (truncation toward zero,
   which Rust's `/` gives natively for signed ints).
4. Normalize to f32 by finding the leading bit of the sum, extracting
   23 mantissa bits with RZ, packing the result.

Expected: 10–100× over this f64 kernel (so ~0.3–3 µs for the workhorse).
Bit-exactness must hold — same corpus gate.

Also worth trying in parallel:
- Skip the `Vec<f32>` copy; read directly from the numpy view in the
  inner loop. Probably ~2× on its own at these sizes.
- Expose a batched entry point that accepts (N, M, K) inputs and processes
  many MMAs per call. The tile-level overhead only amortizes once you
  call with >>1 tile at a time.
