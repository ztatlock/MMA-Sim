# 2026-04-23 — Phase 2.3, aarch64 NEON SIMD

**Status:** landed
**Goal:** vectorize the per-output align+accumulate inner loop using
aarch64 NEON intrinsics. 2-wide on the j-axis (process output columns
`j` and `j+1` together).

## What changed

- [fastmma_rust/src/lib.rs](../fastmma_rust/src/lib.rs):
  - `mod neon`: a tiny NEON helper module. `trunc_shr_v(sig, shift)`
    is the vectorized trunc-toward-zero right shift — abs/xor-sub
    trick to correct the sign-aware arithmetic shift that `vshlq_s64`
    gives us natively.
  - `fused_mma_step_int_neon`: SIMD inner kernel. Same pre-decompose
    and product-collection as the scalar path; the k+1-term align+sum
    runs in `i64x2` (two adjacent j outputs per iteration).
  - `mma_f32_out_batched_simd`: PyO3 entry alongside the existing
    `mma_f32_out_batched`. Non-aarch64 builds fall back to the scalar
    kernel silently.
  - `run_one_tile_simd`: per-tile dispatch with the same split-K
    handling as the scalar version.
- [fastmma/rust_ref.py](../fastmma/rust_ref.py): `mma.call_batched_simd(A, B, C)`. Shared
  `_prep_batched` helper (cast, contiguify, TF32 mask) between the
  scalar and SIMD paths.
- [bench/batched.py](../bench/batched.py): column for per-tile SIMD timing and a
  `simd/scalar` ratio; runs both versions on the same stacked batch
  and validates each is bit-exact against the corpus.

## Interpretation

**1.2–1.3× wall-time gain — below the theoretical 2× for 2-wide SIMD.**
Three reasons:

1. **The SIMD-able fraction is small.** The per-output work is
   decompose-C + product-collection (k iterations of scalar mul/add/max) +
   SIMD align+sum + normalize. Only the align+sum (k+1 `i64x2` ops) runs
   vectorized. The k-loop for products is still scalar. At k=16 split-K,
   the SIMD portion is maybe 30% of per-output time.
2. **`trunc_shr_v` is heavier than scalar.** Scalar trunc is one signed
   division (~12 cycles). NEON version is xor/sub/neg/shift/xor/sub (≈6
   ops, ~6 cycles per lane). So per-lane SIMD is ~2× throughput, not
   higher.
3. **Apple M-series has very wide scalar int dispatch.** M-series can
   issue 6+ integer ops per cycle; the scalar kernel was already close
   to backend-limited. 2-wide NEON doesn't dramatically unblock anything
   the scalar core couldn't already do.

On an x86 machine with AVX-512 we'd get 8-wide `i64` ops, which would
amplify the SIMD-able portion's speedup. But the overall fraction stays
the same — probably 2–3× total on AVX-512, not 8×.

## Bit-exactness notes

No iteration needed — the SIMD version passed the corpus first run.
Key point: integer addition of aligned terms is associative and
commutative, so the SIMD reduction order doesn't matter as long as each
individual term's alignment is identical. The `trunc_shr_v` sign-abs-
shift-resign sequence produces the same integer as the scalar
`x / (1 << n)` for all inputs we tested.

## What's next

Phase 2.4 — **rayon parallelism over the batch**, measured against the
pre-SIMD scalar baseline (Phase 2.2) for a clean comparison with SIMD.
We keep `mma_f32_out_batched` scalar-serial, add a new
`mma_f32_out_batched_rayon` that splits the batch loop across worker
threads. On an 8-core machine, expected 4–8× per-tile improvement for
large batches (amortizing thread-dispatch cost).

Phase 2.5 — **combine SIMD + rayon** once both are established
individually. Naive expectation: multiplicative (~1.25× × ~6× ≈ 7–8×),
but NUMA / cache effects can erode that. Worth measuring directly.

## Code housekeeping

- `#[cfg(target_arch = "aarch64")]` guards keep the SIMD path out of
  x86 builds. Non-aarch64 `mma_f32_out_batched_simd` silently runs the
  scalar kernel — same API, no bit-exactness risk, just no speedup.
- `#[target_feature(enable = "neon")]` on the NEON functions. With
  aarch64 as the target triple, NEON is baseline-available on all
  supported CPUs; the attribute is mostly documentation.
