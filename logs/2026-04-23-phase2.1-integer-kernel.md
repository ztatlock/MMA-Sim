# 2026-04-23 — Phase 2.1, integer fixed-point Rust kernel

**Status:** landed
**Goal:** replace the f64 inner loop with pure integer arithmetic. No
more `libm::frexp` / `f64::powi` / `libm::trunc` per term. Keep the same
external API and corpus gate.

## What changed

- [fastmma_rust/src/lib.rs](../fastmma_rust/src/lib.rs) rewritten. New pieces:
  - `decompose(f32, min_exp, nfb) -> (i64, i32, bool)`: decompose from
    raw f32 bits to a signed i64 significand at scale 2^nfb, with
    subnormal flush at the source dtype's min_exp. Handles f32 normals,
    f32 subnormals (full normalize), zero quirk, and NaN/Inf passthrough.
  - `trunc_shr`: signed trunc-to-zero right shift. Rust's `>>` on signed
    is arithmetic (rounds toward −∞) which is different from what we
    want; use `x / (1 << n)` so the semantics match `math.trunc`.
  - `fast_pow2(n)`: 2^n via direct f64 biased-exponent construction.
    Replaces `f64::powi` for the one-per-output normalization.
  - Stack-allocated decomposition buffers (`[i64; MAX_ELEMS]`) — zero
    heap allocation inside the kernel.
  - Zero-copy input slicing (`PyReadonlyArray2::as_slice`), with a Vec
    fallback if the numpy array isn't contiguous. Python wrapper already
    calls `np.ascontiguousarray`, so the fast path always hits.

The f64 NaN/Inf pre-sum is still there — an `if !fp_sum.is_finite()`
short-circuit per output. Cheap, matches upstream behavior exactly.

## Results

5/5 supported instructions bit-exact. Timings via `bench.validate` (which
wraps torch → numpy → Rust; some overhead not in the kernel itself):

| label       | phase 2 (f64) | phase 2.1 (int) | speedup vs oracle |
|-------------|---------------|-----------------|-------------------|
| volta-f16   | 0.012 ms      | 0.010 ms        | 165×              |
| turing-f16  | 0.021 ms      | 0.011 ms        | 369×              |
| ampere-f16 ⭐| 0.036 ms      | **0.016 ms**    | **493×**          |
| ampere-bf16 | 0.067 ms      | 0.035 ms        | 253×              |
| ampere-tf32 | 0.032 ms      | 0.017 ms        | 367×              |

Direct microbenchmark (no torch/validator wrapper):

```
ampere-f16 zeros:  6.9 µs/call    (all-zero decompose fast path)
ampere-f16 random: 11.8 µs/call   (real work)
-> fixed overhead ~6.9 µs, real kernel work ~5 µs
-> 9400 µs -> 11.8 µs = 800x
```

## Interpretation

The integer kernel is **~2× faster** than the f64 Rust kernel (36 µs →
16 µs on the workhorse, 12 µs direct). Not as dramatic as I hoped — two
reasons:

1. **Fixed per-call overhead is ~7 µs**: PyO3 boundary (GIL, argument
   unpacking, result boxing), numpy array creation for the output Vec,
   per-element decomposition of all inputs. The pure inner-loop math is
   maybe 5 µs. We're already at ~60% efficiency before even touching the
   kernel.
2. **The f64 kernel was already pretty tight** once `frexp` and `powi`
   were the only transcendentals. The integer version saves those, but
   the workload is ~2048 products — not enough to show a 10× gap over
   fast f64.

The shape tells us the next lever: **batching**. At 7 µs fixed cost per
call, 800× per single MMA translates to ~4000× if we call with 32 tiles
at a time (amortizing the boundary) and nothing else changes. Beyond
that, SIMD on the inner loop would help at larger batch sizes.

## Bit-exactness notes

The integer decomposition required some care to match upstream exactly:

- **f32 subnormals**: `frexp` normalizes them to sig in [1, 2) × 2^exp;
  in int, we find the top mantissa bit and shift to scale 2^nfb. The
  inferred `exp = top_bit − 149` reproduces the frexp exponent.
- **Subnormal flush at `min_exp`**: upstream multiplies sig by 2^(e−min_exp),
  a lossless f64 op. In int at scale 2^nfb, this is a right shift of a
  non-negative value. For the dtypes we care about (f16/bf16/tf32 cast
  up to f32) the shifted-out bits are always zero (the cast pads mantissa
  with zeros matching the shift depth), so the shift is also lossless.
- **Signed trunc toward zero**: not what Rust's `>>` does on negatives.
  Use `/ (1 << n)` instead. Caught in the initial draft by the corpus.
- **Zero quirk**: upstream sets `exp = −126` when sig becomes 0, regardless
  of the original exponent. Replicated post-flush.

Corpus caught zero mismatches on the integer kernel's first run — the
f64 version had already shaken out the parameter-threading bugs.

## What's next

Phase 2.2 — **batched entry point**. Rewrite `mma_f32_out` to accept
`(B, M, K) / (B, K, N) / (B, M, N)` inputs and loop inside Rust. This
amortizes the 7 µs fixed cost over B tiles. Realistic expectation: at
B=32, per-tile cost drops to ~5 µs (just the inner work), getting us
from 800× to ~2000× on the workhorse.

Phase 2.3 — **SIMD on the inner loop**. The i64 accumulation is
embarrassingly parallel across (M, N) output pairs. On AVX-512 we can
do 8 i64 adds per instruction; on NEON, 2. Probably another 4–8× at
the larger batches.

Phase 2.4 — **coverage**: extend to f64 (pairwise with Rust FMA intrinsic),
fp8 (already should work with different `out_mantissa_bits`, just needs
SUPPORTED update and min_exp for fp8 dtypes), then block-scaled. These
are mostly plumbing, not performance work.
