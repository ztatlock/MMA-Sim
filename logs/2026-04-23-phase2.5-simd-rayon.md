## Stacking analysis

For each fixture, does `s+r/sc` match `simd/sc × rayon/sc`?

| label       | naive (s × r) | actual (s+r) | Δ     |
|-------------|---------------|--------------|-------|
| volta-f16   | 9.39          | 9.76         | +4%   |
| turing-f16  | 7.61          | 7.34         | −4%   |
| ampere-f16  | 9.66          | 9.76         | +1%   |
| ampere-bf16 | 13.51         | 11.80        | −13%  |
| ampere-tf32 | 12.53         | 12.22        | −2%   |

**Stacking is within measurement noise of multiplicative**, with one
exception (ampere-bf16 at −13%). That fixture was already the slowest
scalar baseline; the likely reason is memory-bandwidth contention as
16 NEON-busy threads hammer the shared L3 and memory subsystem at the
same time. Not a dealbreaker; 11.8× is still better than either axis
alone.

The textbook reading: rayon gives each thread less external work to
do; SIMD gives each thread less *inner* work to do; they attack
different bottlenecks and don't fight each other much.

## How to interpret the 10⁶× goal

The original framing — "1 million times faster" — was for the overall
simulator throughput. Zoom out:

- On a **per-tile** basis we're at ~10⁴×. The remaining ~10² would
  need GPU offload or aggressive specialization (fully-unrolled
  kernels per dtype combo, 4-wide SIMD via AVX-512 or SVE).
- On a **full-workload** basis (say simulating a 1024×1024×1024 GEMM
  as 10⁶ tiles), the oracle takes ~10⁶ × 10 ms = ~3 hours. We take
  ~10⁶ × 1 μs = ~1 second. That is a 10⁴× real workload speedup.
- The only way to credibly get 10⁶× on full workloads is **GPU**. A
  single modern GPU could plausibly do 10⁶ tile-equivalent ops/sec
  per SM; with 100+ SMs, ~10⁸ ops/sec. Simulating "simulator on GPU"
  is feasible because our kernel is pure integer arithmetic, which is
  GPU-friendly.

So the honest scoreboard has a hard CPU ceiling around 2–5 × 10⁴×
per-tile with further effort (kernel specialization, tighter
register allocation, maybe 4-wide NEON via pairs). To cross 10⁶× we
have to change substrate — either accept the target was aspirational,
or commit to a CUDA/Metal port.

## What's next

Phase 2 is effectively done. Natural branches from here:

1. **Phase 3: coverage.** Extend the kernel to f64 (pairwise with
   hardware FMA), fp8 (already supported by flag, just wire the
   SUPPORTED table), fp4 + block-scaled. More instructions, same
   performance profile.
2. **Phase 4: specialization.** Use Rust const generics or codegen
   to emit per-`(arch, dtype)` kernels with constants inlined,
   k-loop unrolled, branches elided. Probably 2–3×.
3. **Phase 5: GPU.** If the real ambition is 10⁶× on full GEMMs,
   port the integer kernel to Metal (on this box) or CUDA (on a
   server). Same corpus gate, different binary target.
4. **Call it.** 10⁴× per-tile, bit-exact across 5 instruction types,
   is already an honest research result. Worth writing up even if we
   don't push further.

Worth a conversation about which branch matters — "further" is a
diminishing-returns slope and the remaining gap needs a substrate
change more than a micro-optimization.
