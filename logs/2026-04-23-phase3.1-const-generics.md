# 2026-04-23 — Phase 3.1, const-generic specialization across 5 instructions

**Status:** landed (all 5 supported instructions bit-exact, specialized)
**Goal:** generalize Phase 3.0's hand-specialized ampere-f16 kernel into
a const-generic template. Emit one monomorphization per supported
(arch, qualifier); dispatch from Python.

## What changed

- [fastmma_rust/src/lib.rs](../fastmma_rust/src/lib.rs): `ampere_f16` module renamed to
  `specialized`. New const-generic kernels:
  - `decompose_narrow<const MIN_EXP, const NFB>` — f16/bf16 inputs,
    skips the f32-subnormal path, scales to 2^NFB.
  - `decompose_f32_src<const NFB>` — tf32/f32 inputs, full subnormal
    handling.
  - `step_narrow<M, N, K, NFB, A_MIN, B_MIN>` / `step_f32<M, N, K, NFB>`
    — the generic kernel dispatchers.
  - `inner<M, N, K, NFB>` — shared per-output NEON inner loop.
- `run_batched_specialized` — PyO3 helper wrapping shape check, zero-copy
  slicing, and rayon-parallel per-tile dispatch. Takes the per-tile
  closure as an `F: Fn + Sync`.
- Five PyO3 entries:
  - `mma_spec_ampere_f16`: M=16, N=8, K_HALF=8, NFB=24, narrow(-14,-14), split-K
  - `mma_spec_ampere_bf16`: M=16, N=8, K_HALF=8, NFB=24, narrow(-126,-126), split-K
  - `mma_spec_ampere_tf32`: M=16, N=8, **K_HALF=4**, NFB=24, step_f32, **split-K**
  - `mma_spec_turing_f16`: M=16, N=8, K=8, NFB=24, narrow(-14,-14), no split
  - `mma_spec_volta_f16`: M=8, N=8, K=4, **NFB=23**, narrow(-14,-14), no split
- [fastmma/rust_ref.py](../fastmma/rust_ref.py): `_SPECIALIZED_FNS` dict dispatches
  `call_batched_specialized` by `(arch, qualifier)` to the right
  PyO3 symbol.
- [bench/batched.py](../bench/batched.py): `spec` column now populated for all 5 fixtures.

## Bugs caught during the rollout

The corpus caught three bugs on the first run — all worth documenting
since they're the kind of thing that'd quietly corrupt production:

1. **NFB hardcoded to 24 in `decompose`.** Phase 3.0 shipped with
   `sig_q24 << 1` (i.e., scale = 2^24) baked in. Volta has NFB=23.
   Fix: thread NFB as a const-generic parameter; shift is `NFB - 23`.
2. **Ampere-tf32 actually uses split-K.** I had assumed "no split
   because k=8", but the oracle explicitly sets `is_split_k = True`
   when `arch in {Ampere, AdaLovelace} && k == 8 && a_type == float32`
   ([nv_ptx.py:36-49](../mmasim/simulator/nv_ptx.py:36)). Two passes of K_HALF=4. Missing this
   gave 502/2048 mismatches on every tf32 sample.
3. **`#[inline(always)]` + `#[target_feature]` is unstable** on current
   rustc. Dropped `inline(always)` from `inner`; the generic
   monomorphization inlines it anyway.

The third was a compile error, but 1 and 2 both only surface when the
corpus validator runs — which is why it exists.

## Scoreboard updates (absolute per-tile speedup over oracle)

| instruction | oracle (μs) | specialized (μs) | speedup |
|-------------|-------------|------------------|---------|
| volta-f16   | 1970        | 0.245            | 8040×   |
| turing-f16  | 4780        | 0.465            | 10280×  |
| ampere-f16  | 9400        | 0.581            | 16180×  |
| ampere-bf16 | 9190        | 0.618            | 14870×  |
| ampere-tf32 | 7420        | 0.304            | 24410×  |

All five now **past 10⁴×**. Ampere-tf32 crosses **2.4 × 10⁴×** — the
highest ratio so far on any tile. (Reason: tf32's data has only 11
significant bits per operand, so the int products are small and well
under any precision/overflow bounds; less work per tile.)

## Why spec/s+r varies so much

- Volta (1.10×): tiny kernel (k=4), per-tile overhead dominates. The
  work wasn't the bottleneck — boundary + allocation already was.
- Turing (1.46×): k=8, some real math to specialize, but no split-K.
- Ampere-f16/bf16 (2.0× / 1.8×): k=16 split-K with NFB=24, plenty
  of work to compile-out; k=8 unrolls cleanly, narrow decompose saves
  branches.
- Ampere-tf32 (2.97×): bigger specialization win because the generic
  kernel's f32-subnormal branch is dead code for tf32-masked inputs
  and the compiler couldn't prove it without the const-generic hint.

Pattern: **the more work per tile, the more specialization buys you.**
The volta case is near the overhead floor. The ampere cases still have
headroom (maybe another 1.5× via 4-wide NEON pairs or k-unrolled
register scheduling).

## Running ceiling estimate

- Specialized workhorse (ampere-f16): 0.581 μs = **16 180×** over oracle.
- Specialized best (ampere-tf32): 0.304 μs = **24 410×**.
- 10⁶× target: 0.0094 μs (9.4 ns/tile). Still ~50–80× away on CPU.

The retrospective's "2–5 × 10⁴" CPU ceiling estimate is holding up:
we're at the low end now. Further CPU work (4-wide NEON via paired
i64x2 vectors, software-pipelined k-unroll, maybe specializing the
output-normalize f32 cast) could plausibly double this to 4–5 × 10⁴.
10⁵× clearly needs GPU.

## What's next

The user framing was: push limits on both specialization and GPU, then
come back to coverage + rigorous validation. Phase 3.1 is the end of
the "push specialization" branch for CPU; one more round (3.2) could
try 4-wide NEON or better k-scheduling, but the payoff is getting
small and the GPU option is where the remaining ~2 orders of magnitude
live.

**Recommended next step: Phase 4 — GPU port (Metal first).** The
specialized kernels are compact and pure integer, ideal as a template.
One kernel per (arch, qualifier) dispatched via Metal shader library;
~1 week of work to get the workhorse running on GPU, ~2 weeks for
full 5-instruction parity.

After that, come back to **coverage** (f64, fp8 beyond the subset,
fp4 unpacking, block-scaled mxfp8/mxfp4, AMD MFMA, wgmma, tcgen05mma)
and **hardware-ground-truth validation** as separate work items.
